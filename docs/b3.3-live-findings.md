# B3.3 — Live paired resume A/B: offline safety survives contact with the model

**Run 2026-08-22. LIVE — spent ~$5 of subscription quota (user-authorized).** Harness
`corpus/b3_live_resume_ab.py`; compiled results in `corpus/analysis/b3-live-results.json`. This is the
one thing the offline mechanical proxy (B3.1) could not settle: when an obsolete tool result is
actually **absent**, does the agent still reach the same fix, or does it break / thrash?

## Mechanism (and its constraint)

The clean design — a custom message-loop A/B — needs a raw API key, which this environment does not
have (SDK auth fails; the only working path is the subscription-OAuth `claude` CLI, which owns its own
context). So retirement was applied the only way the CLI allows: **hand-edit a resumable transcript and
`claude -p --resume` it.** Per task:

1. Truncate a real native (A_native) Step-7 session at a cut turn t*.
2. Reconstruct the worktree state by replaying the edits up to t*.
3. Emit two resumable variants (fresh UUID session ids): **FULL** (unchanged) and **RETIRED** (the
   tool-result content of every B3-retired object — superseded, or abandoned tail at tail_turn+5 —
   replaced with a stub).
4. Resume both with the same continuation prompt, budget-capped, and compare: same files edited? does
   RETIRED have to re-read what we retired?

Confirmed en route that resume loads an edited transcript and the agent reasons from it correctly (on
a 1-turn probe it named `django/db/models/expressions.py` as its next edit — the real fix target).

## Results (3 tasks, 1 cut × 1 rep each)

| task | T | t* | retired objs | FULL edited | RETIRED edited | same fix? | retirement-induced extra re-reads |
|---|--:|--:|--:|---|---|:--:|--:|
| django-10554 | 134 | 58 | 29 | expressions.py | expressions.py | ✅ | +1 (expressions.py) |
| django-11138 | 122 | 43 | — | base.py, operations.py, utils.py | base.py, operations.py, utils.py | ✅ | 0 |
| django-14608 | 47 | 25 | 12 | *(none — fix already complete)* | *(none)* | ✅ | 0 |

**3/3 tasks: the RETIRED arm reached the same fix as the FULL arm.** Total extra re-reads caused by
retirement, across all three: **one**.

## What the live run shows

1. **Retirement did not break the task.** In every case the agent, continuing from a context with the
   obsolete tool outputs stubbed, edited the same source files as the full-context arm (and as the
   original native run). No thrash, no wrong target, no dead end.
2. **The re-reads that happened were not caused by retirement.** In 11138 both arms re-read `base.py`
   exactly 3 times; in 10554 both re-read `expressions.py` (FULL once, RETIRED twice). Agents re-read a
   file right before editing it *regardless* of whether an earlier read is still resident — so retiring
   that earlier read costs ~nothing. The only retired object ever re-read was the edit **target**.
3. **Non-target retired objects were never re-read.** `query.py`, `compiler.py`, `tests.py`,
   `timezone.py`, and the retired bash outputs — the abandoned tail — were not re-accessed at all,
   confirming they were genuine dead weight.

This is consistent with B3.1's mechanical 95–99% safety, and slightly **stronger**: even the
edit-target reads that B3.1's D0/D1 flags as "unsafe to retire" turn out to cost ~nothing live, because
the agent re-reads them for the Edit anyway. The offline model treated those re-references as a cost;
the live run shows they are largely free.

## Caveats (this is a tiny, hacky probe — treat it as a sanity check, not a verdict)

- **n = 3 tasks, one cut point, one rep per arm.** The model is non-deterministic; a single rep can't
  bound the break rate. This confirms *existence* of safe behavior, not a rate.
- **No pass/fail grading.** Without docker/linux there is no SWE-bench verification; "same fix" means
  the RETIRED arm edited the **same source files** as the full-context and native runs — a strong
  proxy, not a proven pass.
- **Mechanical (over-)retirement.** I retired the raw superseded+tail set, *not* B3.1's safety-filtered
  subset — so this is if anything a harder test than the policy B3 would actually ship, and it still
  held.
- **Reconstructed state.** The worktree was rebuilt by replaying edits up to t*; replay can drift, and
  a bug (since fixed) meant pre-cut *scratch*-file edits didn't apply — but the cuts were before any
  *source*-file edits, so source files sat at clean base in **both** arms, and the paired comparison is
  unaffected.
- **Mechanism ≠ production.** This edits a resumable transcript; it is not the live history transformer
  a real deployment needs. It tests the *effect* of retirement on the agent, not a shippable mechanism.

## What B3.3 does and does NOT establish (scope discipline)

- **It answers the SAFETY question, not the savings question.** B3.3 shows that *removing* retired
  context did not derail the continuation. It does **not** measure a whole-session token saving. The
  ~8–11% figure is **offline-modeled** (B3.1), not live-demonstrated here.
- **It is effectively two active fixes plus one inert case.** For django-14608 the cut landed after
  the fix was already complete, so neither arm had substantive work — it contributes a "no spurious
  re-reads" data point, not an informative fix.
- **There is no clean live cost comparison.** 10554 RETIRED cost slightly *more* than FULL
  ($0.528 vs $0.482) with one extra re-read; 11138's FULL cost was not captured; 14608 was cheaper in
  RETIRED but had no remaining work. With n=3, one rep, and stochastic trajectories, none of this
  measures savings in either direction — it only shows retirement did not obviously break or thrash.

## Verdict

The last open question was framed as *safety*, and on this small sample it comes back **yes**:
retroactive retirement of dead context did not change which fix the agent reached in any of the three
cases, and imposed essentially no re-read tax. That removes the specific worry that the offline double
digits were an unsafe mirage the way prospective compaction (B2.3) was — but it is a **safety sanity
check, not a live measurement of the 8–11%.**

Stated precisely, the program's strongest validated result is now: **~8–11% *modeled* safe additive
single-window token-residency reduction (increasing with session length), plus a small live A/B showing
no obvious semantic failure from removing retired context.** Not "8–11% live-demonstrated saving" — that
statement is not yet supported.

Every offline lever is quantified and the one live risk has a first empirical check. What would raise
confidence is scale (dozens of tasks × reps) with real pass/fail grading, and a production history
transformer — none available at zero further cost here. Frozen B1, the B2 artifacts, and the G1/G2
closure were not touched; the original 10554 session and all worktrees were restored/removed after the
run. The next milestone is **B4 — Production Context GC feasibility** (`docs/b4-context-gc-feasibility.md`,
`B3_DECISION.md`), not another measurement round.
