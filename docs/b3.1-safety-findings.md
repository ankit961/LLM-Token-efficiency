## The question, and why retroactive should win where B2.3 lost

B3.0's double-digit ceiling rides the **abandoned tail** — retire an object once its key is last
touched. That is not provably safe: the agent might re-need the content. B2.3 asked the same "did
compaction break a later step?" question for *prospective* file compaction and got a **decisive no**:
22% edit-recall, **78% of edits forced a re-read**, because the agent needs a file's body to make its
first edit and prospective compaction removed it before that edit.

Retroactive retirement should invert that result for a structural reason: **an Edit is itself a
touch**, so a file stays resident *through* its edit — a retired object is by construction never one
the agent is about to edit. The only residual risk is the agent **re-needing** a retired object's
content *afterwards*. B3.1 measures exactly that, sweeping a staleness lag L (retire at last_touch + L
turns), with two conservative mechanical break signals:

- **D0 — RE-REFERENCE:** a later tool call (turn > retire) whose input names the retired object's file
  path — the agent went back to that file via *any* tool (cat, grep, re-open at a new offset). Missed
  by exact supersession keys, so a genuine miss.
- **D1 — CONTENT-REUSE:** a later Edit whose `old_string` shares a distinctive source line (≥20
  non-space chars) with the retired object's content — the agent edited code it last saw there.

An object is unsafe at lag L if D0 or D1 fires after its retire turn. Supersession retirements (a newer
version exists) are provably safe and always counted.

## What this establishes

1. **The tail is mostly safe — the opposite of B2.3.** Where prospective compaction broke 78% of
   edits, retroactive retirement is **95–99% safe**. The structural hypothesis holds: keeping a file
   live through its last touch means retirement almost never removes something still in use.
2. **~82% of the speculative tail is SAFELY realizable.** On long (≥100-turn) sessions the B3.0 +tail
   ceiling is ~13.5%; the SAFE realized NET at lag 5 is **11.1%** — the safety tax is only ~2.4pp.
3. **A small lag buys the last bit of safety cheaply.** L=5–10 lifts safe_fraction (0.95→0.96 long,
   0.977→0.988 short) for a modest saving cost. Recommended operating point: **L≈5–10**.
4. **On single-window sessions this NET is PURELY ADDITIVE.** All 60 django sessions fit one context
   window — native `/compact` never fired — so there is no native-compaction overlap to subtract here.
   The ~8% (short) / ~11% (long) safe NET is unopposed by any existing mechanism. (Overlap only
   competes beyond one window, i.e. the giant — see caveats.)

## Skeptical caveats

- **D0/D1 are mechanical proxies, and bracket rather than pin the truth.** D0 (any later mention of the
  path) *overcounts* unsafe — a path mention is not always a real re-need — which pushes safe_fraction
  *down* (conservative). Neither signal catches **pure semantic reliance** (the agent reasons from a
  retired read without re-accessing it or editing matching lines), which would push safe_fraction *up*
  beyond what's real. The measured 95–99% is therefore a mechanical bracket; a live run is the only way
  to pin the semantic residual. This is the same mechanical-vs-semantic boundary flagged in B2.2/B2.3.
- **One task family** (django SWE-bench), n=19 long sessions; the giant point is multi-window/overstated.
- **The saving is counterfactual** — no live run confirms the token-turns avoided.
- **Native-compaction overlap is still unmeasured for multi-window sessions.** B3.1 shows single-window
  retirement is additive; the marginal value *over* native `/compact` on very long sessions (where the
  saveNET is largest) remains the one open modelling piece.

## Verdict

The key risk on B3 — that its double digits were an unsafe mirage, as prospective compaction turned out
to be — **does not materialize**. Retroactive context retirement is **95–99% mechanically safe**, and
~82% of the +tail ceiling is safely realizable: **~8% (short) / ~11% (long) NET, purely additive on
single-window sessions.** That makes it, by a wide margin, the strongest and safest token lever this
program has found.

Two things still gate a live build, and both are honest unknowns rather than red flags: (1) a **live
confirmation** that the mechanical safe-fraction survives contact with real semantic reliance, and (2)
the **marginal-over-native-`/compact`** NET on multi-window sessions. Per the standing directive, no
live run and no transformer were built here — B3.1's job was to retire the safety risk, and it has.
Frozen B1, the B2 artifacts, and the G1/G2 closure were not touched.
